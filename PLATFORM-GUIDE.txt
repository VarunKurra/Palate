YOUR SALES / SETUP WORKFLOW
1. Sign into the staff workspace and choose Add restaurant.
2. Add its name, unique menu address and optional owner email.
3. Open Menu. Import a CSV or Palate JSON file, use the sample dishes, or add
   dishes manually. Sample images are copied into that restaurant's storage.
4. Upload real food photos where available. Label generated images as AI
   illustrations. Confirm prices, ingredients and allergen labels with the shop.
5. Set branding, restaurant details, language content and any featured special.
6. In Demo requests, connect the owner's request to the restaurant and approve
   it. This grants owner membership. Alternatively create a private invitation in
   Team and send its link directly to the intended owner.
7. Set the restaurant to Active. It must have at least one dish. Its menu becomes
   public and the owner's dashboard unlocks. Setup or paused restaurants remain
   inaccessible to guests and are not editable by owners.
8. Share the link and QR code. Owners can now maintain their menu themselves.

SUPABASE DESIGN
This is a multi-tenant database: one scalable shared set of tables, with a
restaurant_id on each restaurant-owned record. It does not create a separate
table or database for every shop. Row-level policies enforce isolation.

public.restaurants: identity, slug, status, branding/settings and plan amounts.
public.restaurant_members: verified user-to-shop memberships (owner/editor).
public.restaurant_invitations: email-based access waiting to be claimed.
public.palate_staff / staff_invitations: protected Palate team roles.
public.demo_requests: signup/demo workflow, one request per user.
public.menu_categories / menu_items / menu_deals: tenant-scoped menu records.
public.menu_events: anonymous menu interactions and source/language metadata.
public.support_tickets: customer support and staff responses.
public.audit_log: changes to restaurant and menu records.
private.request_limits: short-lived server-side recommendation usage limits.
Storage bucket menu-media: restaurant UUID / unique filename.

Images are deliberately public menu assets. Uploads, updates, listing and deletes
are restricted to the restaurant's authorized users or Palate staff. SVG and
non-image uploads are rejected. Individual images have a 10 MB limit.

Anonymous users cannot select private account or restaurant tables. A narrowly
scoped get_public_menu function returns only guest-facing data for active shops.
Members cannot change activation or grant staff privileges. Staff privileges
come from protected database rows, never editable account metadata.
The public key in frontend code is intentionally publishable. No service-role
key, database password, SMTP password or AI key is shipped to the browser.

SQL migrations are in supabase/migrations, applied to the supplied project and
registered in Supabase migration history. Future migrations can use the normal
Supabase CLI workflow. Do not re-run the initial schema manually on an existing
project. The tenant access test uses a transaction and rolls all fixtures back.

ANALYTICS
Visits are distinct anonymous sessions, refreshed after inactivity. Dish views
count detail panels opened; saves count additions to a shortlist. Engagement is
the share of sessions with a dish view, save, special or recommendation event.
Reports include date ranges, daily traffic, popular dishes, sources, languages
in the data payload, recommendation counts, special views and CSV export.
These are menu interactions, not purchases, revenue or order conversions.
Browser-reported events can contain bots; they are not financial records.
Known signed-in restaurant editors are excluded from browser analytics.
Do Not Track and Global Privacy Control suppress browser event collection.

RECOMMENDATIONS — CONNECTION READY, AI KEY NOT CONFIGURED
The deployed Supabase function recommend uses actual published menu items.
Without a provider key it uses the tested local meal-selection rules. It checks
course, availability, dietary filters and budgets. The guest menu also falls
back locally if the service is unavailable. There are no invented menu items.

To enable the optional Gemini connection later:
1. Copy .env.example to .env.local (the latter is ignored and must stay private).
2. Set GEMINI_API_KEY and confirm GEMINI_MODEL is available in that account.
3. Run: supabase secrets set --project-ref opxmijpsppojwpogvfwd --env-file .env.local
4. Run: supabase functions deploy recommend --project-ref opxmijpsppojwpogvfwd --use-api
5. Deploy the translation function too: supabase functions deploy translate-menu --project-ref opxmijpsppojwpogvfwd --use-api
6. Check the response mode is "ai" with a real menu request and review a translation draft.
ALLOWED_ORIGINS must include the eventual website origin before public hosting.
No AI-provider calls were tested because no key was supplied. The deployed
rule-based fallback was tested. The service limits usage per restaurant and
client; generated IDs are validated against current menu content before use.

LANGUAGES
The sample menu has 80 complete machine-assisted translations, previously
spot-checked and context-corrected. Live restaurants keep their own translated
content in Supabase; sample restaurant text never overwrites it. A language is
enabled after the owner supplies its categories, dish names/details/ingredients,
restaurant information where present, and featured special. The optional Translate with AI button creates a reviewable draft using the same
Gemini connection. It does not publish automatically, and is unavailable until a
provider key is configured. Translation use is limited to 10 requests per shop
per hour. The language editor also accepts manual, reviewed translations.
Custom menu copy should be reviewed by the restaurant before enabling a language.
